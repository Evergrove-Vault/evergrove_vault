# 📝 Overview
Разбор **GraphRAG SDK 1.0** от FalkorDB: модульный асинхронный пайплайн построения графа знаний с настраиваемой онтологией, слиянием новых документов с существующим графом и **изоляцией данных разных арендаторов на уровне данных**. Для этого списка важнее всего честная оговорка авторов: *добавление* знаний поддерживается, а *автоматическое снятие устаревших фактов* — нет.

> [!attention] Про источник
> Это блог вендора (дата публикации 29.04.2026, обновлён 28.09.2026), бенчмарки запускали сами авторы.

> [!important] Чего нет в моих заметках
> Есть общая рекомендация про «Incremental updates» в [[GraphRAG (Microsoft)]], но нет разбора, чего не умеют даже «промышленные» SDK: инвалидация устаревших фактов и изоляция арендаторов.

# 💡 Решения
**Пайплайн.** Async-first архитектура с паттерном «стратегия» на каждом этапе; отдельные фазы — приём документов, финализация графа, поиск. По словам автора, это упрощает встраивание в существующие сервисы.

**Онтология.** По умолчанию — 11 общих бизнес-понятий (люди, организации, продукты, события и др.); домен расширяется наследованием схемы. Изменение онтологии после загрузки требует повторного извлечения по затронутым документам (по описанию в блоге), поэтому схему стоит продумать заранее — ср. [[information extraction]].

**Слияние вместо пересборки.** При появлении новых или изменённых документов SDK вливает их в существующий граф, «preserving the current graph state and adding new entities and relationships incrementally».

**Устаревшие факты — прямая оговорка авторов:** «automatic removal of outdated or superseded facts is currently a roadmap item, not a shipped feature. Teams working with rapidly changing factual data should build a manual invalidation step into their update workflow». Для этого нужны провенанс и версии фактов: [[Provenance графа и безопасное удаление документов]], [[Bi-temporal факты - Zep и Graphiti]].

**Изоляция арендаторов.** Изолированные графы для клиента, команды или пользователя внутри общей среды; «each tenant's graph is separated at the data layer, not just at the query layer». Это ответ на риск утечки между арендаторами: [[Безопасность RAG - poisoning, ACL и происхождение данных]].

**Поиск.** Многопутевой: обход графа + семантический поиск с объединением ранжированных результатов.

# 📊 Данные из блога
- GraphRAG-Bench (Novel; общий балл): FalkorDB SDK **63,73**, AutoPrunedRetriever 63,72, G-Reasoner 58,94 — фактически ничья с лидером. SDK сильнее в фактах (65,22 против 45,99), AutoPrunedRetriever — в контекстной суммаризации (83,10 против 69,54).
- Скорость приёма: 21–33 с на документ, ≈53 мин на 100 документов, ≈10 ч на 1000; авторы подчёркивают, что узкое место — пропускная способность извлечения, а не мощность самого FalkorDB. Отсюда важность чекпоинтов: [[Инкрементальная индексация - хеши, идемпотентность, мемоизация]].

# ⚠️ Ограничения
Замеры вендора; нет независимой проверки; утверждение про долю провальных enterprise-RAG (72–80%) в блоге приведено со ссылкой на безымянный «анализ 2026 года», поэтому цифру использовать не стоит.
