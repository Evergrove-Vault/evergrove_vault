# 📝 Overview
Руководство с кодом: как превратить **Markdown-протоколы встреч** в граф Neo4j (встречи, участники, задачи, ответственные), который **сам обновляется** при изменении файлов. Пример важен как *готовый шаблон* «Markdown → структурированное извлечение → разрешение сущностей → граф → инкрементальные обновления» — почти в точности задача для Obsidian-волта.

> [!important] Чего нет в моих заметках
> [[information extraction]] описывает IE как теорию (NER + RE + события), а [[graph RAG]] — граф как идею. Рабочего сквозного примера, где схема, извлечение, слияние и обновление собраны вместе, нет.

---

# 💡 Как это работает
**Фаза 1 — извлечение по файлам.** Markdown режется по заголовкам (`#` или `##`); каждый раздел отдельно отправляется в LLM через библиотеку `instructor`, которая заставляет модель вернуть данные, соответствующие Pydantic-схемам: `ExtractedMeeting` (дата, исходные заметки, организатор, участники как `ExtractedPerson`, задачи с ответственными). Родственная тема — [[SO]] (structured output). В примере LLM по умолчанию — `openai/gpt-5-mini`; результат кэшируется (`memo=True`).

**Фаза 2 — разрешение сущностей.** Сырые имена по всем встречам дедуплицируются: эмбеддинги → пары-кандидаты → подтверждение LLM → каноническое имя. Подробности — [[Entity resolution - эмбеддинги и LLM-судья]].

**Фаза 3 — объявление графа.** Три типа узлов (`Meeting`, `Person`, `Task`), три типа рёбер: `ATTENDED` (участник → встреча, с флагом `is_organizer`), `DECIDED` (встреча → задача), `ASSIGNED_TO` (человек → задача). Первичные ключи (`id`, `name`, `description`) обеспечивают идемпотентность.

**Инкрементальность.** Изменённые файлы обнаруживаются и обрабатываются заново, для неизменённых разделов берётся кэш LLM, в граф пишутся только отличающиеся узлы и рёбра; исчезнувший файл удаляет свои узлы и рёбра. Оценка авторов — «99%+ reduction in LLM API costs for a typical 1% daily churn». См. [[Инкрементальная индексация - хеши, идемпотентность, мемоизация]].

**Фреймворк.** CocoIndex ([GitHub](https://github.com/cocoindex-io/cocoindex), Apache-2.0) — ядро на Rust, Python API, модель «Target = F(Source)»: вы объявляете желаемое состояние целевого хранилища, движок держит его синхронным с источником и отслеживает lineage «до исходного байта». Цели: реляционные и векторные БД, графовые БД; источники: файлы, репозитории, почта и др.

# 🤔 Применимость к моему волту (идея, не проверенный вывод)
Явный граф между заметками у меня уже есть через внутренние ссылки Obsidian. Извлечение добавило бы **неявный слой**: люди, решения, задачи, технологии, упомянутые в тексте, и связи «кто/что/когда». Ограничения: русскоязычный текст (качество NER/LLM-извлечения надо проверить), омонимы имён, стоимость на ~100 заметках небольшая и упирается в кэш.

# ⚠️ Ограничения
Учебный пример с тремя типами сущностей; блог вендора; ключ узла = имя человека, что не защищает от омонимов.
