# 📝 Overview
Как убедиться, что обновлённый индекс **действительно** отвечает по актуальным данным, и как хранить версии, чтобы можно было отвечать «на дату». Три идеи: (1) быстро меняющиеся структурированные данные не индексировать, а спрашивать «вживую» через SQL; (2) документы обновлять на уровне изменившихся чанков и хранить метаданные актуальности; (3) **тестировать** актуальность: одновременно держать в индексе старую и новую версию и проверять, что ответ берёт новую.

> [!attention] Про источник
> Страница Oracle отвечает HTTP 403 на автоматическую загрузку, поэтому её содержание сверено только по выдержкам поисковика и описаниям соседних статей того же блога. Формулировки ниже — пересказ выдержек, не прямые цитаты со страницы.

> [!important] Чего нет в моих заметках
> В [[оценка качества RAG]] и [[building the Entire RAG Ecosystem and Optimizing Every Component#Основные метрики для оценки качества в RAG/GraphRAG|метриках RAG/GraphRAG]] качество оценивается на статичном корпусе. Метрик и тестов на *устаревание* и *удаление* нет. # 💡 Что предлагают

## 1. Живые строки — не документы
Операционные данные (заказы, остатки, статусы) запрашивают напрямую SQL или NL2SQL; поиск по эмбеддингам оставляют для документов, транскриптов и политик. Принцип из выдержки: «real-time RAG should not re-embed every changing record».

## 2. Метаданные актуальности
Для проиндексированных документов отслеживают: временные метки источника, хеши чанков, версию эмбеддинг-модели, флаг «текущая версия», состояние удаления. Переэмбеддятся только изменившиеся чанки (см. [[Инкрементальная индексация - хеши, идемпотентность, мемоизация]]). В соседней статье про оценку прод-RAG добавлены фильтры по арендатору, правам, источнику, статусу, свежести и версии документа.

## 3. Набор freshness-тестов (моя сводка из трёх статей Oracle)
| Тест | Подготовка | Что проверять |
|---|---|---|
| Удалённый документ | удалить источник, запустить синхронизацию | запросы по его уникальным фактам не возвращают его чанки и цитаты |
| Вытеснение версии | в индексе одновременно старая и новая версия | ответ и цитата из новой; старая не в топ-k |
| Изменённый чанк | поменять один абзац | заменён только его чанк, остальные не переэмбеддились |
| Дубли эмбеддингов | загрузить один текст дважды | дубликаты подавлены |
| Смена версии парсера/эмбеддера | переиндексировать часть корпуса | нет смеси эмбеддингов разных версий |
| Кэш | семантический кэш ответов | после обновления не отдаёт старый ответ |

Формулировка из выдержки: «a production RAG system is fresh only if source updates, deletes, parser changes, embedding changes, cache invalidation, and retrieval filters are observable and tested». Стоит держать *устаревшие и текущие* случаи в одном оценочном наборе, чтобы регрессии свежести были видны.

## 4. Версии и «поиск на дату» (LiveVectorLake)
Двухслойная схема ([arXiv:2601.05270](https://arxiv.org/abs/2601.05270), препринт): «горячий» слой (Milvus с HNSW) хранит только текущие чанки и отвечает быстро; «холодный» (Delta Lake / Parquet) хранит всю историю версий; запрос с датой маршрутизируется в нужный слой. Заявлено: до 100 мс на текущих знаниях, до 2 с на временных запросах, 10–15% переобработки при обновлении. Оценка на 100 документах, пять версий — это ранний результат.

## 5. Как строить свежий тестовый набор (FreshStack)
[FreshStack](https://arxiv.org/abs/2504.13128) автоматически собирает бенчмарки по быстро растущим техническим темам: корпус кода и документации, «нагеты» из вопросов сообщества, поддержка на уровне нагета. Наблюдения авторов: готовые ретриверы заметно уступают oracle, а реранкеры не улучшают первую стадию на двух из пяти тем. Метод нагетов — в [[Nugget-оценка RAG - AutoNuggetizer]].

# ⚠️ Ограничения
- Тесты Oracle — инженерные рекомендации, не бенчмарк; порогов приёмки нет.
- LiveVectorLake и FreshStack — препринты; на малых корпусах результаты могут не переноситься.
- Не проверяют устаревание *внутри графа* — для него нужны версии фактов: [[Bi-temporal факты - Zep и Graphiti]].

# 🧭 Где встроить в HUB RAG
Группа «Метрики качества RAG» получает вторую ось — *свежесть*: в дополнение к faithfulness/correctness/contextual relevancy добавляются pass/fail-тесты удаления и вытеснения. В «предобработке запроса» появляется правило маршрутизации: «изменчивая структурированная информация → SQL», ср. [[retrieval#Routing Retrieval]].
