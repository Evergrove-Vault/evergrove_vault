# 📝 Overview
Как обновлять векторный и графовый индекс при изменении источников, не пересобирая всё с нуля: находить изменившиеся документы по хешу, кэшировать дорогие LLM-вызовы и записывать результат идемпотентно. Три независимых источника (граф на AWS, граф встреч в Neo4j, версионируемая векторная база) приходят к одной и той же схеме.

> [!important] Чего нет в моих заметках
> В [[graph RAG#Dynamic Graph Update]] описано *что* делать с новым текстом (NER + RE → новые узлы и связи), а [[GraphRAG (Microsoft)#Ограничения и риски]] лишь констатирует, что живой корпус требует переиндексации. Механики «как понять, что именно пересчитать» и «как не платить за LLM дважды» в заметках нет.

# 💡 Как это работает

## 1. Реестр хешей документов
- Каждый документ получает хеш содержимого, хеш хранится в реестре (в AWS-фреймворке — необязательная таблица DynamoDB).
- При следующем запуске «unchanged documents are skipped, new or changed documents are re-extracted» и вливаются в живой граф через идемпотентные upsert-операции. Логика дельты вынесена в `incremental.py` репозитория [awslabs/unified-kg-rag-on-aws](https://github.com/awslabs/unified-kg-rag-on-aws).

## 2. Мемоизация LLM-извлечения
- В CocoIndex Markdown режется по заголовкам (`#`/`##`), каждый раздел отдельно извлекается LLM (`instructor` + Pydantic-схемы). Функция помечена `memo=True`: пока текст раздела и модель не менялись, результат берётся из кэша, «an unchanged section is never re-extracted».
- Модель и эмбеддер объявлены как ключи контекста с `detect_change=True`: смена модели автоматически перезапускает только затронутые шаги.
- Оценка авторов: «99%+ reduction in LLM API costs for a typical 1% daily churn» (это их расчёт для 1% ежедневных изменений, а не независимый замер).

## 3. Первичные ключи → идемпотентная запись
- Узлы графа имеют естественные ключи (`Meeting.id`, `Person.name`, `Task.description`), поэтому повторная запись неизменённого — no-op («the graph write is a no-op for anything that did not change»).
- Исчезнувший исходный файл → его узлы и рёбра удаляются на следующем прогоне («items whose source file disappeared are removed»).

## 4. Хеш на уровне чанков (векторная сторона)
- LiveVectorLake (препринт «work in progress», [arXiv:2601.05270](https://arxiv.org/abs/2601.05270)): content-addressable синхронизация чанков по SHA-256 — детерминированное обнаружение изменений без внешнего хранилища состояния.
- На корпусе из 100 документов в пяти версиях переобрабатывается 10–15% контента против 100% при полной переиндексации. Подробнее про горячий/холодный слои — в [[Freshness-тесты и версионирование индекса]].

## 5. Чекпоинты стадий
- 12-стадийный пайплайн AWS сохраняет состояние после каждой стадии; прерванный прогон возобновляется флагами `--pipeline-id` и `--resume-from-stage`, кэш можно синхронизировать с S3.
- Это не роскошь: по данным блога FalkorDB, узкое место — пропускная способность извлечения (21–33 с на документ, порядка 10 часов на 1000 документов), см. [[GraphRAG SDK (FalkorDB) - онтология и изоляция тенантов]].

```
документ ─ хеш совпал? ── да ──▶ пропустить
              │ нет
              ▼
      разбить на разделы (по заголовкам)
              ▼
  для каждого раздела: кэш[хеш(текст) + модель]?
        есть ──▶ взять результат      нет ──▶ вызвать LLM, сохранить
              ▼
  upsert узлов и рёбер по ключам; удалить артефакты исчезнувших источников
```

# ⚠️ Ограничения
- **Изменение текста ≠ инвалидация факта.** Хеш скажет, что документ поменялся, но не скажет, какие ранее извлечённые факты стали ложными. FalkorDB пишет прямо: «automatic removal of outdated or superseded facts is currently a roadmap item, not a shipped feature». Нужны provenance и версии фактов: [[Provenance графа и безопасное удаление документов]], [[Bi-temporal факты - Zep и Graphiti]].
- **Замечание (мой вывод, в источниках не сказано):** кэш по хешу чанка ломается, если правка сдвигает границы всех последующих чанков. Структурная нарезка по заголовкам (как в CocoIndex) стабильнее нарезки фиксированным окном, см. [[21 Chunking Strategies for RAG]].
- Иерархические сводки (community reports, RAPTOR) после точечной правки нужно пересчитывать выборочно: как это делают TG-RAG и TagRAG — [[TG-RAG - временной граф знаний]], [[TagRAG - иерархия тегов вместо сообществ]].
