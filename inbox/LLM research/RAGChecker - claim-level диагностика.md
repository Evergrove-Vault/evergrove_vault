# 📝 Overview
**RAGChecker** раскладывает ошибки RAG на *ретривер* и *генератор* с помощью проверки **на уровне утверждений** (claims): ответ и эталон разбираются на атомарные утверждения, и каждое проверяется на следование из другого текста (entailment). Вместо одной оценки «хорошо/плохо» получается набор диагностических метрик, которые показывают, *где* ломается система. Работа принята в трек Datasets & Benchmarks NeurIPS 2024, код открыт: [amazon-science/RAGChecker](https://github.com/amazon-science/RAGChecker).

> [!important] Чего нет в моих заметках
> В [[building the Entire RAG Ecosystem and Optimizing Every Component#Основные метрики для оценки качества в RAG/GraphRAG|метриках]] заявлены Faithfulness, Correctness, Contextual Relevancy на уровне ответа; в [[оценка качества RAG]] — метрики графа. Метрик, которые *разделяют* вклад поиска и генерации на уровне отдельных фактов, нет. [[ragas]], [[deepeval]] и [[grouse]] в волте пока пустые заметки.

# 💡 Как это работает
1. **Text-to-Claim Extractor** разбивает ответ, эталон и найденные чанки на атомарные утверждения.
2. **Claim-Entailment Checker** проверяет, следует ли утверждение из другого текста. В статье оба шага делает Llama3-70B-Instruct через RefChecker.
3. Метрики считаются по тому, какие утверждения ответа подтверждены эталоном и чанками.

# 📊 Метрики (определения из статьи)
| Группа | Метрика | Смысл |
|---|---|---|
| Общие | precision | доля верных утверждений среди всех утверждений ответа |
| | recall | доля утверждений эталона, покрытых ответом |
| | F1 | гармоническое среднее |
| Ретривер | `claim_recall` | доля утверждений эталона, присутствующих в найденных чанках |
| | `context_precision` | доля релевантных чанков (содержащих хотя бы одно утверждение эталона) среди k |
| Генератор | `faithfulness` | доля утверждений ответа, следующих из найденных чанков |
| | `context_utilization` | доля найденных нужных утверждений, попавших в ответ |
| | `noise_sensitivity_in_relevant` | неверные утверждения ответа, взятые из *релевантных* чанков, среди всех утверждений |
| | `noise_sensitivity_in_irrelevant` | то же из *нерелевантных* чанков |
| | `hallucination` | неверные утверждения, которых нет ни в одном чанке |
| | `self_knowledge` | верные утверждения, которых нет в чанках (модель «знала сама»; для RAG чем меньше, тем лучше) |

**Что изучали:** 8 систем — 2 ретривера (BM25, E5-Mistral) × 4 генератора (GPT-4, Mixtral-8x7B, Llama3-8B, Llama3-70B). Мета-оценка: значительно лучшая корреляция с оценкой людей, чем у других метрик.

**Выводы авторов о компромиссах:**
1. *Полнота ретривера ↔ чувствительность генератора к шуму:* чем больше нужных утверждений в чанках, тем больше шума получает генератор.
2. Открытые модели проявляют «chunk-level faithfulness»: доверяют релевантному чанку целиком, включая шум, в отличие от GPT-4, который отбирает выборочно.
3. Явные требования в промпте создают напряжение между `context_utilization` и `noise_sensitivity`: улучшая одно, чаще ухудшаем другое.

**Практика (README):** `ragchecker-cli --input_path=… --output_path=… --extractor_name=… --checker_name=…`; вход на запрос — `query_id`, `query`, `gt_answer`, `response`, `retrieved_context` (список чанков с `doc_id` и `text`); модели экстрактора и чекера настраиваются.

# ⚠️ Ограничения
- Нужен **эталонный ответ** (`gt_answer`) для каждого вопроса: без размеченного набора метрики ретривера не считаются.
- Оценка зависит от качества извлечения утверждений и от LLM-чекера (в примере — Llama3-70B); это стоимость и источник шума.
- Работа 2024 года; проверена на английских данных.
