# 📝 Overview
**Temporal GraphRAG (TG-RAG)** делает граф знаний *временно́-осознанным*: одинаковые факты в разные моменты времени хранятся как **разные рёбра**, а сводки строятся по иерархии времени (год → квартал → месяц → день). Новые документы добавляются без полной пересборки: пересчитываются сводки только новых листовых узлов времени и их предков.

> [!important] Чего нет в моих заметках
> Про время в графе в заметках нет ничего: [[GraphRAG (Microsoft)]] строит сообщества и сводки без временной оси, а [[graph RAG#Dynamic Graph Update]] говорит только «добавляем узлы и связи». Вектора и обычные графы плохо различают «выручка 2021» и «выручка 2022» — это проблема, с которой начинают авторы.

# 💡 Как это работает
**Двухуровневый граф**
1. *Временной граф знаний*: рёбра — отношения с меткой времени (четвёрки «сущность, сущность, отношение, время»). Несколько фактов между одной парой сущностей в разное время хранятся как параллельные рёбра, так видна эволюция отношений.
2. *Иерархический граф времени*: все уникальные метки складываются во вложенные корзины (год → квартал → месяц → день); межслойные рёбра связывают узлы времени с активными в этот период отношениями.

**Извлечение**: для каждого чанка LLM сначала находит метки времени, затем нетемпоральные сущности, затем временны́е отношения; метки нормализуются.

**Временны́е сводки**: для каждого узла времени снизу вверх LLM пишет краткий отчёт о заметных событиях окна; сводки поднимаются по иерархии, получая многоуровневое представление (мелкие события и крупные тренды).

**Обновление**: из новых документов извлекаются новые четвёрки и вливаются в граф; отчёты генерируются для новых листовых узлов времени и обновляются вдоль путей к предкам. Полная регенерация всех сводок, как в GraphRAG, не нужна.

**Ответ на вопрос**: LLM выделяет во вопросе временны́е узлы; берутся top-K рёбер по косинусной близости и фильтруются по временному охвату запроса. Локальный поиск использует Personalized PageRank от отфильтрованных по времени стартовых сущностей; глобальный собирает лучшие чанки и временны́е отчёты, LLM выделяет атомарные тезисы с оценкой уверенности и отбрасывает самые слабые под размер контекста.

# 📊 Результаты
Набор **ECT-QA** создан авторами: 480 стенограмм звонков по отчётности (earnings call) 24 компаний из 5 секторов за 2020–2024 годы, 1,58 млн токенов; 1005 конкретных вопросов (483 на один момент, 321 на интервал, 201 «до/после»), 100 абстрактных; 261 неотвечаемый. Протокол проверяет три сценария: базовые вопросы на базовом корпусе, базовые вопросы после пополнения корпуса, новые вопросы после пополнения.

| Метод | Построение индекса, токенов prompt/completion | Доля верных (базовый корпус) | Стоимость обновления, prompt/completion | Доля верных, новые вопросы |
|---|---|---|---|---|
| **TG-RAG** | 6,3M / 7,1M | **0,599** | 1,6M / 2,0M | **0,617** |
| GraphRAG | 37,1M / 17,7M | 0,405 | 30,0M / 7,8M | 0,398 |
| LightRAG | 17,1M / 9,0M | 0,406 | 4,6M / 2,6M | 0,382 |
| HippoRAG2 | 3,2M / 1,1M | 0,410 | 0,8M / 0,3M | 0,372 |
| NaiveRAG | — | 0,385 | — | 0,390 |

Числа из таблиц III и IV статьи. Обратите внимание: HippoRAG2 обновляется дешевле TG-RAG, но заметно чаще отвечает неверно или отказывается.

# ⚠️ Ограничения
- В описании обновления речь идёт о **пополнении** корпуса; исправление и удаление документов отдельно не разбираются (для них нужны версии фактов и провенанс: [[Bi-temporal факты - Zep и Graphiti]], [[Provenance графа и безопасное удаление документов]]).
- Корпус (отчётные звонки) строго привязан ко времени; на текстах без датировки польза метода неочевидна.
- Качество зависит от извлечения меток времени LLM.

# 🧭 Где встроить в HUB RAG
Блок «для graph DB» — для корпусов, где важна хронология (новости, отчёты, протоколы, журналы изменений). Аналог иерархических сводок из [[building the Entire RAG Ecosystem and Optimizing Every Component#Hierarchical Indexing (RAPTOR) Knowledge Tree]], но с осью времени и дешёвым обновлением. В «предобработке запроса» нужен шаг «определить временной охват вопроса».
