# 📝 Overview
**SLCA-GRPO** («Resolving Cross-Segment Credit Misattribution in Tool-Calling RL») решает структурную проблему обучения агентов с инструментами: траектория смешивает *разные по природе* сегменты — рассуждение и структурированный вызов инструмента, вывод инструмента, итоговый текст для пользователя. Если единая награда за траекторию раздаётся всем токенам одинаково, шум и вариативность итогового текста «протекают» в градиенты токенов, принимающих решение о вызове. Предложение — **Segment-Locked Credit Assignment (SLCA)**: у каждого сегмента свой канал награды.

> [!important] Насколько это про RAG
> Косвенно: RL-обученные поисковые агенты ([[Search-R1 - RL для поисковых агентов]]) устроены так же (рассуждение → запрос → результат → ответ). Заметок про обучение агентов в волте нет, а принцип «выбор инструмента, аргументы, рассуждение и подача ответа оцениваются раздельно» применим и к оценке готовых пайплайнов. Для эксплуатации это пока исследовательское направление, а не готовый рецепт.

# 💡 Как это работает
- **Проблема («global signal conflation»):** GRPO-подобные алгоритмы «broadcast a unified trajectory-level advantage to all tokens». Авторы приводят диагностический случай: верный итоговый текст может скрыть неверную или неэффективную траекторию вызовов, а неверный итог может подавить правильное использование инструментов.
- **Сегментация:** по маске «обучаемый токен / замороженный контекст среды». Сегмент *summary* — последний непрерывный отрезок обучаемых токенов; сегмент *tool* — объединение всех предыдущих.
- **Раздельные награды:** `R_tool` — плотная награда за процесс (структура, имя, ключи, значения аргументов, параллелизм вызовов); `R_sum` — предпочтение по итоговому ответу (LLM-судья). Преимущества нормируются в группе *отдельно*, затем направляются *только* своим токенам: токены вызова получают только награду процесса, токены итога — только награду ответа; штраф за пропуск обязательного вызова уходит в итоговый сегмент.
- **Гарантия:** градиент токенов вызова не зависит от награды итога.
- **Установка:** основной бэкбон Qwen2.5-7B (также 3B и Qwen3-8B); данные Toucan; проверка на Berkeley Function-Calling Leaderboard и τ²-Bench.

# 📊 Результаты
«SLCA-GRPO … outperforms standard GRPO, ToolPO, and RLTR by +2.53 pp on in-domain evaluation, +1.36 pp on BFCL, and +9.15 pp on τ²-Bench under the same training budgets». Результаты усреднены по трём запускам.

# ⚠️ Ограничения (названы авторами)
- Нужна чёткая граница между вызовами инструментов и свободным текстом; встроенная генерация кода потребует обучаемой сегментации.
- Награда процесса опирается на сопоставление с эталонными траекториями и может недооценивать допустимые альтернативные последовательности вызовов.
- Внутри сегмента вызовов одна скалярная награда идёт на все токены — временное распределение (какое из нескольких действий сработало) не решено; комбинация с VinePPO, GiGPO, SPO не проверялась.
- Масштаб (7B) и симулированные инструменты; сравнения с реальными API — вперёди.

# 🧭 Где встроить в HUB RAG
Группа «reasoning» — как замечание к обучаемой политике поиска: не награждать «поисковые» токены за красоту финального ответа. Для *оценки* пайплайна: считать отдельные метрики для этапов «запрос/выбор инструмента» и «итоговый ответ» ([[оценка качества RAG]], [[RAGChecker - claim-level диагностика]]).
