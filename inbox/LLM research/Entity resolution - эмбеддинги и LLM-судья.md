# 📝 Overview
Entity resolution (ER) — приведение разных написаний одной сущности («Sarah», «Sarah Chen», «S. Chen») к одному узлу графа. Современный шаблон дешёвый: **эмбеддинги отбирают пары-кандидаты, а LLM подтверждает слияние только для них**. Так делают CocoIndex и Zep; LightRAG и HippoRAG 2 идут проще или мягче.

> [!important] Чего нет в моих заметках
> В [[information extraction#Классический пайплайн (модульный)]] упомянута coreference resolution («он» = «Илон Маск»), а в [[Relation Extraction]] — entity linking к внешнему графу (Wikidata). Внутренней **канонизации и слияния** сущностей в собственном графе (без внешней базы) в заметках нет, хотя качество графа зависит от неё сильнее, чем от выбора модели RE.

# 💡 Четыре подхода
| Подход | Как работает | Источник |
|---|---|---|
| **Кандидаты по эмбеддингам + LLM-судья** | эмбеддинги имён (`SentenceTransformerEmbedder`) → пары по порогу сходства → `LlmPairResolver` подтверждает → каноническое имя; интерфейс `.canonicals()` и `.canonical_of(raw_name)`; узел `Person` ключуется каноническим именем | CocoIndex, граф встреч |
| **Эмбеддинги + полнотекстовый поиск + LLM** | новая сущность эмбеддится, ищутся кандидаты косинусным и полнотекстовым поиском по существующим узлам, LLM по промпту решает, дубль ли; при дубле генерируются обновлённые имя и summary | Zep / Graphiti (статья) |
| **Дедупликация функцией `D(·)`** | одинаковые сущности и отношения из разных чанков объединяются на этапе индексации | LightRAG |
| **Мягкие связи вместо слияния** | добавляются «synonym edges» между фразами с эмбеддинг-сходством выше порога, узлы остаются раздельными | HippoRAG 2 |

Что именно слито, влияет на всё дальше: при слиянии узел должен унаследовать **все источники** обоих (иначе часть фактов «осиротеет», см. [[Provenance графа и безопасное удаление документов]]).

# ⚠️ Риски и как с ними жить (мои выводы из сравнения)
- **Ложное слияние дороже дубликата.** Два разных «Ивана Петрова» в одном узле портят все ответы через этот узел; два узла одного человека лишь снижают полноту. Поэтому порог для автослияния стоит ставить высоким, а спорные пары либо отдавать LLM с дополнительными атрибутами (роль, организация, e-mail), либо связывать мягким ребром как в HippoRAG 2.
- **Стоимость.** LLM вызывается только для пар-кандидатов, а не для всех сочетаний (иначе O(N²)); ср. проблему квадратичной сложности в [[information extraction#Graph Prediction (предсказание графа связей)]].
- **Ключ узла = имя** (как в примере CocoIndex) удобен для идемпотентной записи, но чувствителен к омонимам; для реального корпуса нужен суррогатный идентификатор.
- Решение о слиянии стоит журналировать (кто, когда, по какой паре) — иначе ошибку нельзя откатить.

# 🧭 Где встроить в HUB RAG
Группа «IE, NER, RE»: отдельный шаг **после NER и до записи в граф**. Для канвы это недостающая стрелка между «NER» и «для graph DB». Граф аргументов ([[argument mining]]) выигрывает тоже: одинаковые утверждения из разных текстов должны становиться одним узлом.
