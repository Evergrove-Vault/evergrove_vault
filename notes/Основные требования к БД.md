## **1. ACID (для реляционных баз данных)**

ACID — это свойства транзакций, гарантирующие целостность данных:

1. **Atomicity (Атомарность)**
    - Транзакция выполняется полностью или не выполняется вовсе.
    - Пример: перевод денег между счетами: либо списание и зачисление проходят вместе, либо ни одно не выполняется.
2. **Consistency (Согласованность)**
    - После транзакции база данных остаётся в корректном состоянии, соблюдая все ограничения (например, внешние ключи, уникальные поля).
    - Пример: сумма всех счетов в банке не изменится после перевода.
3. **Isolation (Изолированность)**
    - Одновременные транзакции не мешают друг другу, результаты промежуточных операций недоступны другим транзакциям до завершения.
    - Пример: два пользователя одновременно пытаются снять деньги с одного счета — база гарантирует корректное выполнение обоих запросов.
4. **Durability (Надёжность / Долговечность)**
    - После успешного завершения транзакции изменения сохраняются, даже если база упадёт или произойдёт сбой системы.
    - Пример: если транзакция прошла, то деньги списались и зачислились — даже при отключении сервера данные останутся.

> **Где применяется:** классические реляционные БД (PostgreSQL, MySQL, Oracle) — идеальны для финансовых систем, учёта, заказов.

## **2. BASE (для распределённых и NoSQL систем)**

BASE — альтернативная концепция для распределённых, масштабируемых систем, где строгие ACID-транзакции невозможны или слишком дорого обходятся:

1. **Basically Available (В основном доступна)**
    - Система старается быть доступной для запросов, даже если часть узлов недоступна.
2. **Soft state (Мягкое состояние)**
    - Состояние данных может быть временно неконсистентным. Нет гарантии, что все узлы сразу видят одни и те же данные.
3. **Eventual consistency (Конечная согласованность)**
    - В конце концов все узлы придут к одному и тому же состоянию, но может быть временная рассинхронизация.

> **Где применяется:** NoSQL базы (Cassandra, DynamoDB, MongoDB, Redis) — особенно полезно для больших распределённых систем и сервисов, где доступность важнее строгой консистентности.

## **3. CAP теорема**

CAP — это теоретическая модель распределённых систем, которая говорит, что нельзя одновременно получить все три свойства, нужно выбирать два из трёх:

1. **Consistency (Согласованность)**
    - Все узлы видят одинаковые данные в одно и то же время.
2. **Availability (Доступность)**
    - Каждый запрос получает ответ (успешный или ошибку), даже если не все узлы доступны.
3. **Partition tolerance (Устойчивость к разделению / сетевым разрывам)**
    - Система продолжает работать даже при потере связи между узлами

| Выбор двух | Что теряется                                                    | Пример                              |
| ---------- | --------------------------------------------------------------- | ----------------------------------- |
| C + A      | Partition tolerance → при сетевом разрыве сервис может упасть   | Малораспределённая SQL-база         |
| C + P      | Availability → при разрыве часть запросов не сможет выполниться | Блокчейн, распределённые транзакции |
| A + P      | Consistency → данные могут быть временно рассинхронизированы    | NoSQL системы типа Cassandra        |

> В микросервисной архитектуре часто делают выбор в пользу **AP** (доступность + устойчивость к разрыву) для некоторых сервисов (например, кэш, логирование), а для критичных финансовых операций — **CP** (консистентность + устойчивость).
